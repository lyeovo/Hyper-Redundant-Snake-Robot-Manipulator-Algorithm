2.0 白话讲解：一次任务是怎么跑完的先看故事，再看接口

把整套系统想象成一家自动化“分拣与搬运”小车间。下面用大白话把一次任务从头到尾走一遍——你不必先懂任何代码，就能明白每步在干什么。术语会先出现在括号里，后面接口小节再讲字段。

① 任务单来了 —— 视觉系统下单

上层的视觉模块（SpaceSnakeVisionUI）用相机看到目标（比如桌上的一个零件），在“相机视角”下算出它的位置和朝向，然后写下一张任务单（TaskCommand）。这张单子不是直接塞给机器人的，而是以一个 .json 小文件（CMD-xxx.json）放进一个共享收件文件夹（outbox）。好比把订单投进了“任务邮箱”。

② 守门人常驻 —— runTaskLoop 一直盯着邮箱

叫 runTaskLoop 的程序一直醒着，每隔 1 秒看一眼邮箱。一看到新单子，就把“文件”读成“程序能处理的格式”（jsondecode）。要是单子坏了读不出来，就把它丢到一边（改名 .bad）继续等下一单，绝不卡住。

③ 拆单 —— taskExecute 把“一件事”拆成“一串动作”

拿到单子，taskExecute 先做三件安全检查：整机是否被急停（estop）？是否被明确禁止执行（allow_execute）？目标识别够不够可信（置信度）？任何一条不满足就直接拒单（REJECTED），绝不启动。没问题后，它把任务拆成若干小步骤（段）。比如“抓起来再放到别处”（pick_and_place）会拆成 5 段：靠近 → 抓 → 抬 → 挪到放置位置 → 松开。

④ 翻译位置 —— taskToSegments / projectTo2D

视觉给的是“相机视角下的 3D 坐标”，可机械臂是在水平平面上工作的。所以先把坐标翻译成平面的 [x, y, 朝向角]，再算出“预抓取点”（目标后 0.15 m 处先停一下）和“放置预取点”，让动作更稳、不容易碰。

⑤ 真正的难题：求解每个段 —— simulateMotion + 共享内核

对每个小步骤，程序要算出每个电机该转多少度，才能让机械臂末端走到那个位置（这就是逆运动学 IK）。这是整个链路里计算最重、最容易失败的部分。它先试最快的梯度法；走不通（被障碍挡住、卡在局部最优）就换更聪明的采样法（RRT*、图引导等），由 auto 调度，每个段最多重试 3 次。

这里的“共享求解内核”就是所有链路共用的同一个“大脑”——不管你是真实任务、仿真界面，还是顶层闭环，只要说“帮我解一个目标”，都进同一个求解器，得到同一套关节角。这样保证“仿真里能走通的，真实任务也走通”。

⑥ 拼成“整车命令” —— 组装 motor_cmd

每个段都解出一小段“关节角快照”。程序把它们首尾拼接成一条完整轨迹：每一行代表某一时刻所有 6 个关节的角度，旁边再配一列“夹爪”指令（在每段的末尾决定张开还是闭合）。这条东西叫 motor_cmd，是给电控的“动作说明书”。

⑦ 交给下游 —— exportMotorCmd

把说明书存成 .mat 或 .csv 文件。真正的电控（dSPACE）离线加载后按时间轴匀速插值去驱动电机。注意：复杂的 IK 求解不会放进实时循环——一次性离线算好，电控只做“确定性回放”。

⑧ 全程“报进度” —— taskWriteStatus

上面每一步，系统都会把“进行到哪、到没到”写回另一个文件夹（inbox），生成一个状态文件。视觉界面轮询这个文件，就能给用户实时显示进度条和当前步骤（比如“正在抓取”）。

⑨ 收尾 —— 防止重复做

任务处理完后，runTaskLoop 会把原单改名成 .done，意思是“这单我处理过了”。这样即使程序重启或重复轮询，也不会把同一个任务做两遍。

为什么只说这条是“关键路径”？因为只有这一条链路的最终产物（motorCmd）会真实驱动电控执行。GUI 仿真、顶层闭环、学习训练都算“在大脑里演练”，只有链路 A 是“真正动手”。

2.1 任务运作情景同一任务在不同判定下走向哪条分支

一条任务从「接收」到「完成/终止」，会因安全校验 → 展开 → 逐段求解 → 急停四个阶段的结果走向不同分支。下表按执行顺序列出全部判定点与产物。error_code=0 只代表“成功走完”，其余码分别映射到不同终止态。

状态机边界：taskExecute 自身只产生 COMPLETED / FAILED / REJECTED / ESTOP_TRIGGERED 四个终态；RECEIVED 由视觉 UI 侧标记、CANCELED 是视觉 UI 可覆盖显示的外部终态，二者不经过taskExecute。运行期的取消通过 simulateMotion 的 'Cancel' 回调与 runTaskLoop 的 estop 传递，而非直接写 CANCELED。

这些情景，用大白话怎么理解？

S1 正常成功：一路绿灯，每个段都解出来了，于是拼好轨迹、存文件、上报“完成”。这是最理想的情况，也是绝大多数任务走的路。

S2–S4 被拒绝：系统在还没动手之前就把单子退了。可能是“整机被急停按钮按下”、可能是“有人明确说这个动作不许执行”、也可能是“视觉识别得太没把握（置信度低于 0.5）”。拒单是好事——宁可不做，也不乱动。

S5 展开异常：走到“拆单”这一步，发现“这个任务类型我不认识”（比如 command_type 打错了）。程序承认自己处理不了，报一个“展开异常”就终止。

S6 目标被障碍吞没：拆单后先检查每个小目标是否安全可达。万一目标点落在障碍物内部（离障碍太近、小于安全距离），就算数学上能解，物理上也够不着，于是直接判“不可达”——而不是硬着头皮去凑。

S7 段求解异常：某个段在运行里真的崩了（程序抛出错误），而不是“没解出来”。为了防止任务做到一半不知道自己在哪，系统立刻终止，把这一单标成失败。

S8 段失败·重试耗尽：某个段试了 3 次都解不出（比如被障碍困住、陷入局部最优）。系统如实上报“这一步没搞定”，并带着这一步的失败码结束。

S9 运行中急停：正在执行中，操作员按下急停。系统每段开始前都查一次急停信号，一旦触发立即 STOP——绝不把这一段动作继续做完。

S10 / S11：这两条发生在“守门人”那一层，跟具体任务内容无关——一个是“单子是坏的，扔一边”，一个是“处理好、标记已做，别重复”。

此外，不同 command_type 会展开成不同段数/夹爪动作，这本身就是一种“任务变体情景”。以 pick_and_place 为例（approach_dist=0.15，lift_h=0.10，θ 为段目标朝向角）：

#段名目标位姿 [x,y,θ]gripper含义
1MOVING_TO_PREGRASPtgt − 0.15·[cosθ, sinθ, 0]0退到预抓取点（沿目标朝向反方向）
2GRASPINGtgt2到目标 / 段末闭合
3LIFTINGtgt − 0.10·[cosθ, sinθ, 0]0后撤“抬离”（平面内沿末端朝向，垂直抬离由电控/垂直轴处理）
4MOVING_TO_PLACEdest − 0.15·[cosθ, sinθ, 0]0退到放置预取点

dest 缺省为 tgt + [0.6, 0, 0]（目标旁 0.6m），否则取 cmd.destination.pose_base 经 projectTo2D 投影。其余 command_type 段数见 架构总览.html §5（move_near_target 1 段、pick_target 3 段、dock_to_interface 2 段、home 1 段）。

E5 · taskExecute → simulateMotion（逐段）：si = simulateMotion(model, method, q, segs(s).target, 'Snapshot', snapshot_m)

q  = model.cfg.q_init;                     % 任务起点（第 1 段用 q_init）
for s = 1:n_seg
  si = [];                                  % 段级重试 ≤3（采样类随机性）
  for attempt = 1:3
    si = simulateMotion(model, method, q, segs(s).target, 'Snapshot', snapshot_m);
    if si.success, break; end
  end
  q = si.q_final;                           % 下一段的起始构型
end

返回 si（info）：q_snapshot [K×N]、t_seq [1×K]、V_hist、q_final、success、error_code、vel_ok、safety_ok、method_used、stats、meta。simulateMotion 会把 opts 全量透传给方法层。

夹爪规则：gs=zeros(1,Ks); gs(end)=segs(s).gripper（段末触发）。时间偏移：t_off=t_off+ts(end)+1。

内核是四个链路在“求解语义”上的汇合点：simulateMotion 统一入口 + 方法分派 + 后处理；内部再落到 method_auto/method_*，值函数与数学基元为基座。

8状态与错误流转

运行期状态由 taskWriteStatus 逐点写入 inbox；错误码贯穿 simulateMotion → taskExecute → exportMotorCmd。

任务状态机

RECEIVED → ACCEPTED → PLANNING → EXECUTING → COMPLETED
                ↓                        ↓
             REJECTED               FAILED / CANCELED / ESTOP_TRIGGERED

错误码（error_code）

0 成功        6 取消/急停/拒绝
2 未收敛      7 卡住/任务展开异常
3 采样层未达  8 段求解异常
5 位姿反解失败 9 终态碰撞
            10 目标被障碍吞没

错误在哪一层产生、流向哪按 error_code 定位

码产生层触发场景上抛路径
0各方法达到容差 / 采样类达到可达区域info → 组装
2method_momentum/sa迭代耗尽未达标 / 精修未达标方法层 info
3采样类未找到路径（A* 无解/树未达）方法层 info
5simulateMotionq0 为位姿且反解失败直接返回
6runTaskLoop/taskExecute急停 / allow_execute=false / 置信度不足REJECTED/ESTOP_TRIGGERED
7momentum / taskExecute卡住（无进展早停）/ 任务展开异常方法层 / FAILED
8taskExecute段求解抛出异常FAILED（终止任务）
9simulateMotion（后处理）min(obsDistAll(q_final)) < rho0强制 success=false（保护导出）
10taskExecute（预检）段目标被障碍吞没（< rho0）FAILED（不可达）

9依赖与约束

运行依赖

  • MATLAB R2017b+（实测 R2026a），依赖 vecnorm、jsondecode；核心无需 Optimization Toolbox。
  • 与视觉联调需 Python（SpaceSnakeVisionUI，D405 mock/实机）——链路 A 的 TaskCommand 来源。
  • 训练端 Python：train_cvae.py / train_policy.py，产出策略 .mat 供部署。

关键约束

  • 障碍仅存在于仿真（视觉不传障碍）；夹爪为简单状态机（gripper_seq 0/1/2）。
  • IK 迭代求解不进实时循环——dSPACE 只做确定性插值，一次离线求解、在线回放。
  • 文件桥是唯一跨进程边界：outbox（任务）+ inbox（状态）+ .done/.bad（消费标记）。
  • 确定性：method_rl 用 rng(1) 复现；generateDemonstrations/sampleTask2D 支持 seed。
